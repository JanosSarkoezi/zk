# gemini response

Ja, das **Builder-Pattern** (oder eine seiner modernere Varianten) bietet sich hier sehr gut an – vor allem aus zwei Hauptgründen:

1. **Vermeidung des „Telescoping Constructor“-Problems:** Der Hauptkonstruktor des Records hat **12 Parameter**, davon gleich **6 Booleans** hintereinander. Bei der Erzeugung des Objekts verliert man leicht den Überblick (`new InteractionEventData(10, 20, 10, 20, 1, true, false, false, true, false, false, ...)`), was extrem fehleranfällig ist.
2. **Standardwerte (Defaults):** Viele Events haben `clickCount = 1`, keine Modifikatoren gedrückt (`isControlDown = false`, etc.) und kein `activeKey`. Ein Builder erlaubt es, vernünftige Standardwerte zu setzen, sodass beim Aufruf nur die Eigenschaften angegeben werden müssen, die sich vom Standard unterscheiden.

---

### Option 1: Der klassische Record-Builder (Empfohlen für Java 17+)

Da ein `record` immutable ist, lässt sich der Builder am saubersten als **statische innere Klasse** (oder über eine Record-Lösung) umsetzen:

```java
package de.fmc.editor.state;

import javafx.scene.input.KeyCode;
import java.util.Objects;
import java.util.Optional;

public record InteractionEventData(
    double worldX,
    double worldY,
    double sceneX,
    double sceneY,
    int clickCount,
    boolean isPrimaryButtonDown,
    boolean isSecondaryButtonDown,
    boolean isMiddleButtonDown,
    boolean isControlDown,
    boolean isShiftDown,
    boolean isAltDown,
    Optional<KeyCode> activeKey
) {
    // Kompakter Konstruktor für Validierung/Null-Handling
    public InteractionEventData {
        Objects.requireNonNull(activeKey, "activeKey must not be null (use Optional.empty())");
    }

    public boolean isShortcut(KeyCode key) {
        return isControlDown && activeKey.isPresent() && activeKey.get() == key;
    }

    public static Builder builder() {
        return new Builder();
    }

    public static class Builder {
        private double worldX = 0.0;
        private double worldY = 0.0;
        private double sceneX = 0.0;
        private double sceneY = 0.0;
        private int clickCount = 1;
        private boolean isPrimaryButtonDown = false;
        private boolean isSecondaryButtonDown = false;
        private boolean isMiddleButtonDown = false;
        private boolean isControlDown = false;
        private boolean isShiftDown = false;
        private boolean isAltDown = false;
        private Optional<KeyCode> activeKey = Optional.empty();

        public Builder world(double x, double y) {
            this.worldX = x;
            this.worldY = y;
            return this;
        }

        public Builder scene(double x, double y) {
            this.sceneX = x;
            this.sceneY = y;
            return this;
        }

        public Builder clickCount(int clickCount) {
            this.clickCount = clickCount;
            return this;
        }

        public Builder primaryButton(boolean down) {
            this.isPrimaryButtonDown = down;
            return this;
        }

        public Builder secondaryButton(boolean down) {
            this.isSecondaryButtonDown = down;
            return this;
        }

        public Builder middleButton(boolean down) {
            this.isMiddleButtonDown = down;
            return this;
        }

        public Builder control(boolean down) {
            this.isControlDown = down;
            return this;
        }

        public Builder shift(boolean down) {
            this.isShiftDown = down;
            return this;
        }

        public Builder alt(boolean down) {
            this.isAltDown = down;
            return this;
        }

            this.activeKey = Optional.ofNullable(key);
            return this;

                worldX, worldY, sceneX, sceneY, clickCount,

                isControlDown, isShiftDown, isAltDown, activeKey

        }
    }
```

### Option 2: Lombok `@Builder` (Falls Lombok im Projekt ist)

Wenn Lombok in eurem JavaFX-Projekt erlaubt/installiert ist, reduziert sich der Boilerplate-Code drastisch:

```java
package de.fmc.editor.state;

import javafx.scene.input.KeyCode;
import lombok.Builder;
import java.util.Optional;

@Builder(toBuilder = true)
public record InteractionEventData(
    double worldX,
    double worldY,
    double sceneX,
    double sceneY,
    @Builder.Default int clickCount = 1,
    boolean isPrimaryButtonDown,
    boolean isSecondaryButtonDown,
    boolean isMiddleButtonDown,
    boolean isControlDown,
    boolean isShiftDown,
    boolean isAltDown,
    @Builder.Default Optional<KeyCode> activeKey = Optional.empty()
) {
    public boolean isShortcut(KeyCode key) {
        return isControlDown && activeKey.map(k -> k == key).orElse(false);
    }
}
```

### Noch ein Tipp zur Vereinfachung des API-Designs

Neben dem Builder könntest du überlegen, zusammengehörige Felder zu strukturieren oder Methoden zur Vereinfachung anzubieten:

1. **Wrangling von Coordinates:** Statt 4 `double`-Werten könntest du ein JavaFX `Point2D`-Objekt verwenden (`Point2D worldPos`, `Point2D scenePos`), sofern das zu eurem Architekturstil passt.
2. **Optional-Nutzung in `isShortcut`:** Die Methode lässt sich noch etwas eleganter schreiben:
   ```java
   public boolean isShortcut(KeyCode key) {
       return isControlDown && activeKey.filter(key::equals).isPresent();
       // Oder: activeKey.map(k -> k == key).orElse(false);
   }
   ```
3. **Factory-Methoden für JavaFX-Events:** Ergänzend zum Builder kannst du eine Statische Factory-Methode bauen, die direkt aus ein `javafx.scene.input.MouseEvent` oder `KeyEvent` ein `InteractionEventData` macht.

### Ergänzung des Record & Builders um Factory-Methoden

Wir fügen dem Record statische Factory-Methoden `from(...)` hinzu. Da für `worldX`/`worldY` oft Koordinaten transformiert werden müssen (z. B. über eine Kamera oder ein Koordinatensystem deines Editors), bietet es sich an, entweder eine Transformations-Funktion mitzugeben oder Standard-Transformationen bereitzustellen.

```java

import javafx.scene.input.KeyCode;
import javafx.scene.input.KeyEvent;
import javafx.scene.input.MouseEvent;

import java.util.Objects;
import java.util.Optional;
import java.util.function.BiFunction;

public record InteractionEventData(
    double worldX,
    double worldY,
    double sceneX,
    double sceneY,
    int clickCount,
    boolean isPrimaryButtonDown,
    boolean isSecondaryButtonDown,
    boolean isMiddleButtonDown,
    boolean isControlDown,
    boolean isShiftDown,
    boolean isAltDown,
    Optional<KeyCode> activeKey
) {
    public InteractionEventData {
        Objects.requireNonNull(activeKey, "activeKey must not be null (use Optional.empty())");
    }

        return isControlDown && activeKey.filter(key::equals).isPresent();
    }

    // Statische Factory-Methoden für JavaFX Events
    // =========================================================================

     * Erzeugt InteractionEventData aus einem JavaFX MouseEvent.
     *
     * @param event Das JavaFX MouseEvent
     * @param sceneToWorldTransformer Eine Funktion/Lambda, die Scene-Koordinaten (X, Y)
     *                                in Welt-Koordinaten (Point2D) umrechnet.

        Point2D worldPos = sceneToWorldTransformer.apply(event.getSceneX(), event.getSceneY());

        return builder()

            .world(worldPos.getX(), worldPos.getY())
            .clickCount(event.getClickCount())
            .primaryButton(event.isPrimaryButtonDown())
            .secondaryButton(event.isSecondaryButtonDown())
            .middleButton(event.isMiddleButtonDown())
            .control(event.isControlDown())
            .shift(event.isShiftDown())
            .alt(event.isAltDown())
            .build();

     * Vereinfachte Varianten für MouseEvents, falls World-Koordinaten = Scene-Koordinaten sind.
     */
    public static InteractionEventData from(MouseEvent event) {
        return from(event, Point2D::new);
    }

    /**
     * Erzeugt InteractionEventData aus einem JavaFX KeyEvent.
     */
    public static InteractionEventData from(KeyEvent event) {
        return builder()
            .control(event.isControlDown())
            .shift(event.isShiftDown())
            .alt(event.isAltDown())
            .activeKey(event.getCode())
            .build();

    // Builder

        return new Builder();

            return this;

            this.sceneY = y;
            return this;
        }

        public Builder clickCount(int clickCount) {
            this.clickCount = clickCount;
            return this;
        }

        public Builder primaryButton(boolean down) {
            this.isPrimaryButtonDown = down;
            return this;
        }

        public Builder secondaryButton(boolean down) {
            this.isSecondaryButtonDown = down;
            return this;
        }

        public Builder middleButton(boolean down) {
            this.isMiddleButtonDown = down;
            return this;
        }

        public Builder control(boolean down) {
            this.isControlDown = down;
            return this;
        }

        public Builder shift(boolean down) {
            this.isShiftDown = down;
            return this;
        }

        public Builder alt(boolean down) {
            this.isAltDown = down;
            return this;
        }

        public Builder activeKey(KeyCode key) {
```

### Was du daran lernen und mitnehmen kannst:

1. **Trennung von JavaFX-UI und State (Low Coupling):**
   Deine Zustandsklassen (z. B. Editoren oder State Machines) müssen jetzt nicht mehr direkt mit `MouseEvent` oder `KeyEvent` von JavaFX hantieren, sondern arbeiten nur mit deinem neutralen `InteractionEventData`.
2. **Lambda als Coordinate-Transformer (`BiFunction`):**
   Durch die Übergabe von `BiFunction<Double, Double, Point2D>` kann das Event-Handling die Kamera-Transformation deines Editors aufrufen (z. B. `viewport::screenToWorld`), ohne dass `InteractionEventData` deine Kamera-Klasse kennen muss.
3. **Flüssiger Code im Controller/UI-Handling:**
   Im Event-Filter oder Event-Handler schrumpft der Code auf Einzeiler zusammen:

```java
// Im Canvas/Editor-Node:
node.setOnMouseClicked(mouseEvent -> {
    // Wandelt MouseEvent automatisch um + berechnet Weltkoordinaten über Kamera/Viewport
    InteractionEventData data = InteractionEventData.from(mouseEvent, viewport::screenToWorld);

    // An den State Machine / Controller weiterleiten
    editorStateMachine.handleMouseClick(data);
});

node.setOnKeyPressed(keyEvent -> {
    InteractionEventData data = InteractionEventData.from(keyEvent);

    if (data.isShortcut(KeyCode.Z)) {
        editorStateMachine.undo();
    }
});
```

# gemini response

Das ist ein hervorragender Gedanke. Die Idee, **Events auf Aktionen (Runnables/Commands) zu mappen**, ist genau der richtige Weg für einen Editor.

Wenn sich das Verhalten je nach **Zustand (State)** ändert, landest du architektonisch beim **State Pattern** in Kombination mit einer **Action-Map / Command Pattern**.

Hier sind die zentralen Architekturfragen und ein eleganter, sauberer Lösungsansatz:

---

## 1. Maus & Tastatur getrennt oder gemeinsam?

**Empfehlung: Zusammenführen im Matcher/Trigger.**

Es ist meistens unhandlich, Maus und Tastatur strikt zu trennen, weil Editoren oft **kombinierte Aktionen** haben:
* *Klick + Shift* $\rightarrow$ Mehrfachauswahl
* *Klick + Alt + Drag* $\rightarrow$ Klönen / Duplizieren
* *Taste `DELETE`* $\rightarrow$ Löschen (rein Tastatur)
* *Linksklick* $\rightarrow$ Selektieren (rein Maus)

Wenn du Maus- und Tastaturereignisse in einer gemeinsamen Abstraktion (`InteractionEventData`) bündelst, kannst du **einheitliche Trigger** definieren, egal woher der Input kam.

---

## 2. Die Architektur: Event Matcher + Command Pattern

Statt eines einfachen `Map<KeyCode, Runnable>` bauen wir ein **`Map<EventMatcher, Action>`**, da ein Tasten- oder Mausklick nicht nur aus einem `KeyCode` besteht, sondern aus Bedingungen (Modifikatoren, Maustasten, Klickzahl).

### Schritt 1: Das `EventMatcher`-Prädikat

Ein Matcher prüft, ob ein `InteractionEventData` zu einer bestimmten Aktion passt.

```java
package de.fmc.editor.state;

import javafx.scene.input.KeyCode;
import java.util.function.Predicate;

@FunctionalInterface
public interface EventMatcher extends Predicate<InteractionEventData> {

    // --- Nützliche Factory-Methoden für lesbare Matcher ---

    static EventMatcher keyPressed(KeyCode key) {
        return data -> data.activeKey().filter(k -> k == key).isPresent();
    }

    static EventMatcher shortcut(KeyCode key) {
        return data -> data.isShortcut(key);
    }

    static EventMatcher primaryClick() {
        return data -> data.isPrimaryButtonDown() && data.clickCount() == 1;
    }

    static EventMatcher primaryDoubleClick() {
        return data -> data.isPrimaryButtonDown() && data.clickCount() == 2;
    }

    static EventMatcher shiftClick() {
        return data -> data.isPrimaryButtonDown() && data.isShiftDown();
    }

    // Kombinationen von Matchern (z.B. Tastatur + Maus)
    default EventMatcher and(EventMatcher other) {
        return data -> this.test(data) && other.test(data);
    }
}
```

### Schritt 2: Die zustandsspezifische Binding-Table (`InteractionMap`)

Jeder Zustand registriert seine eigenen Reaktionen auf Events. Wir bauen eine Klasse, die Matcher nacheinander evaluiert (oder die Zuordnung kapselt):

```java
package de.fmc.editor.state;

import java.util.ArrayList;
import java.util.List;

public class InteractionMap {

    private final List<Binding> bindings = new ArrayList<>();

    private record Binding(EventMatcher matcher, Consumer<InteractionEventData> action) {}

    public InteractionMap on(EventMatcher matcher, Consumer<InteractionEventData> action) {
        bindings.add(new Binding(matcher, action));
        return this; // Fluent API
    }

    public InteractionMap on(EventMatcher matcher, Runnable action) {
        bindings.add(new Binding(matcher, eventData -> action.run()));
        return this;
    }

    /**
     * Versucht das Event an den ersten passenden Matcher zu übergeben.
     * @return true, wenn eine Aktion ausgeführt wurde.
     */
    public boolean handle(InteractionEventData event) {
        for (Binding binding : bindings) {
            if (binding.matcher().test(event)) {
                binding.action().accept(event);
                return true; // Event konsumiert
            }
        }
        return false; // Kein Handler gefunden
    }
}
```

### Schritt 3: Das State-Pattern (Verbindung zum Editor-Zustand)

Jetzt erstellen wir ein Interface für deine Editor-Zustände (`EditorState`). Jeder Zustand liefert seine individuelle `InteractionMap` oder verarbeitet die Events direkt darüber:

```java
package de.fmc.editor.state;

public interface EditorState {

    // Jeder Zustand definiert seine eigenen Bindings
    InteractionMap getInteractionMap();

    default boolean handleInteraction(InteractionEventData event) {
        return getInteractionMap().handle(event);
    }

    // Lifecycle-Methoden für Zustände
    default void onEnter() {}
    default void onExit() {}
}
```

## 3. Anwendungsbeispiel: Verschiedene Zustände

Jetzt zeigt sich die Stärke der Architektur. Du kannst Zustände wie **SelectState** (Auswahlmodus) und **CreateNodeState** (Element-Erstellmodus) definieren:

### Zustand A: `SelectState` (Normale Interaktion)
```java
public class SelectState implements EditorState {

    private final InteractionMap bindings;
    private final EditorContext context;

    public SelectState(EditorContext context) {
        this.context = context;

        this.bindings = new InteractionMap()
            // Tastatur-Shortcuts
            .on(EventMatcher.shortcut(KeyCode.Z), context::undo)
            .on(EventMatcher.keyPressed(KeyCode.DELETE), context::deleteSelected)

            // Reiner Mausklick -> Element auswählen
            .on(EventMatcher.primaryClick(), event -> {
                context.selectAt(event.worldX(), event.worldY());
            })

            // Shift + Klick -> Zur Auswahl hinzufügen
            .on(EventMatcher.shiftClick(), event -> {
                context.toggleSelectionAt(event.worldX(), event.worldY());
            })

            // Doppelklick -> In den Erstellmodus oder Editormodus wechseln
            .on(EventMatcher.primaryDoubleClick(), event -> {
                context.switchState(new CreateNodeState(context));
            });
    }

    @Override
    public InteractionMap getInteractionMap() {
        return bindings;
    }
}
```

### Zustand B: `CreateNodeState` (Neues Element platzieren)
Derselbe Primärklick tut im `CreateNodeState` etwas völlig anderes:

```java
public class CreateNodeState implements EditorState {

    private final InteractionMap bindings;

    public CreateNodeState(EditorContext context) {
        this.bindings = new InteractionMap()
            // Primärklick erzeugt hier ein neues Element!
            .on(EventMatcher.primaryClick(), event -> {
                context.spawnNodeAt(event.worldX(), event.worldY());
                // Danach zurück zum SelectState wechseln
                context.switchState(new SelectState(context));
            })

            // ESC bricht das Erstellen ab
            .on(EventMatcher.keyPressed(KeyCode.ESCAPE), () -> {
                context.switchState(new SelectState(context));
            });
    }

    @Override
    public InteractionMap getInteractionMap() {
        return bindings;
    }
}
```

## Vor- und Nachteile dieses Ansatzes

### Vorteile:
1. **Extrem hohe Lesbarkeit:** Du siehst im Konstruktor eines Zustands auf einen Blick, welche Tasten/Mausaktionen in diesem Zustand was tun.
2. **Kein riesiges `if/else` oder `switch`:** Weder im Event-Handler noch im Zustand gibt es lange Abfragen.
3. **Sehr leicht erweiterbar:** Neue Kombinationen (z. B. `Alt + Rechtsklick`) erfordern nur eine neue Statik-Methode in `EventMatcher`.
4. **Zustandstrennung:** Die selbe Taste/Aktion (`ENTER`, `Klick`) ruft automatisch die richtige Logik für den aktuellen Zustand auf.

Wie erweitert man dieses Event-System um Continuous-Events wie Mouse-Dragging (z. B. Selektionsrahmen ziehen oder Elemente verschieben)?

---

# gemini response

Um kontinuierliche Aktionen wie **Drag & Drop**, **Selektionsrahmen (Rubberband Selection)** oder **Elemente Verschieben** sauber abzubilden, stößt ein reines Point-in-Time-Event (ein einzelner Klick) an seine Grenzen.

Bei Drags benötigen wir **Stateful Interaction** (Start, Update, End). Dafür erweitert man das System am besten um ein **Gestures / Drag-Handler Pattern**.

---

## 1. Welches Problem müssen wir lösen?

Ein Drag-Vorgang hat einen Lebenszyklus über drei JavaFX-Events hinweg:
1. `MOUSE_PRESSED` $\rightarrow$ **Drag Start** (Startposition merken, z. B. Selektionsrahmen initialisieren)
2. `MOUSE_DRAGGED` $\rightarrow$ **Drag Update** (Aktuelle Position verarbeiten, Differenz $\Delta x, \Delta y$ berechnen)
3. `MOUSE_RELEASED` $\rightarrow$ **Drag End** (Aktion abschließen, Undo/Redo-State speichern)

Damit das Event-System nicht mit Zwischenzuständen überflutet wird, führen wir das Konzept eines **`DragHandler`** ein.

---

## 2. Die Erweiterung: `DragHandler` & `DragMatcher`

### Schritt 1: Das `DragHandler`-Interface

Ein `DragHandler` verwaltet den Zustand *während* des Draggings:

```java
package de.fmc.editor.state;

public interface DragHandler {
    /** Wird einmalig beim Drücken der Maustaste aufgerufen. */
    void onStart(InteractionEventData startEvent);

    /** Wird bei jeder Mausbewegung mit gedrückter Taste aufgerufen. */
    void onDrag(InteractionEventData currentEvent, double deltaX, double deltaY);

    /** Wird beim Loslassen der Maustaste aufgerufen. */
    void onEnd(InteractionEventData endEvent);
}
```

---

### Schritt 2: Erweiterung der `InteractionMap` für Drags

Wir erweitern `InteractionMap`, sodass sie unterscheidet zwischen **Aktionen (Single Events)** und **Drag-Gesten (Continuous Events)**:

```java
package de.fmc.editor.state;

import java.util.ArrayList;
import java.util.List;

public class InteractionMap {

    private final List<Binding> singleBindings = new ArrayList<>();
    private final List<DragBinding> dragBindings = new ArrayList<>();

    // Aktiver Drag-Zustand (null, wenn gerade kein Drag läuft)
    private ActiveDrag activeDrag = null;

    private record Binding(EventMatcher matcher, Consumer<InteractionEventData> action) {}
    private record DragBinding(EventMatcher startMatcher, Supplier<DragHandler> handlerSupplier) {}
    private record ActiveDrag(DragHandler handler, InteractionEventData startEvent) {}

    // --- Standard-Aktionen ---
    public InteractionMap on(EventMatcher matcher, Consumer<InteractionEventData> action) {
        singleBindings.add(new Binding(matcher, action));
        return this;
    }

    // --- Continuous Drag-Aktionen ---
    public InteractionMap onDrag(EventMatcher startMatcher, Supplier<DragHandler> handlerSupplier) {
        dragBindings.add(new DragBinding(startMatcher, handlerSupplier));
        return this;
    }

    // --- Event Handling ---

    /** Aufzurufen bei MOUSE_PRESSED */
    public boolean handlePress(InteractionEventData event) {
        // Prüfen, ob ein Drag gestartet werden soll
        for (DragBinding binding : dragBindings) {
            if (binding.startMatcher().test(event)) {
                DragHandler handler = binding.handlerSupplier().get();
                handler.onStart(event);
                this.activeDrag = new ActiveDrag(handler, event);
                return true;
            }
        }

        // Falls kein Drag-Start matcht, normale Klick-Aktionen prüfen
        return handleSingleEvent(event);
    }

    /** Aufzurufen bei MOUSE_DRAGGED */
    public boolean handleDrag(InteractionEventData event) {
        if (activeDrag != null) {
            double deltaX = event.worldX() - activeDrag.startEvent().worldX();
            double deltaY = event.worldY() - activeDrag.startEvent().worldY();

            activeDrag.handler().onDrag(event, deltaX, deltaY);
            return true;
        }
        return false;
    }

    /** Aufzurufen bei MOUSE_RELEASED */
    public boolean handleRelease(InteractionEventData event) {
        if (activeDrag != null) {
            activeDrag.handler().onEnd(event);
            activeDrag = null; // Drag beendet
            return true;
        }
        return false;
    }

    private boolean handleSingleEvent(InteractionEventData event) {
        for (Binding binding : singleBindings) {
            if (binding.matcher().test(event)) {
                binding.action().accept(event);
                return true;
            }
        }
        return false;
    }
}
```

## 4. Wie der JavaFX-Event-Filter/Handler das ansteuert

In deiner JavaFX Canvas/View-Klasse reichst du die Drei-Phasen-Events einfach an den aktuellen State weiter:

```java
// Bei MOUSE_PRESSED
canvas.addEventFilter(MouseEvent.MOUSE_PRESSED, e -> {
    InteractionEventData data = InteractionEventData.from(e, viewport::screenToWorld);
    currentState.getInteractionMap().handlePress(data);
});

// Bei MOUSE_DRAGGED
canvas.addEventFilter(MouseEvent.MOUSE_DRAGGED, e -> {
    InteractionEventData data = InteractionEventData.from(e, viewport::screenToWorld);
    currentState.getInteractionMap().handleDrag(data);
});

// Bei MOUSE_RELEASED
canvas.addEventFilter(MouseEvent.MOUSE_RELEASED, e -> {
    InteractionEventData data = InteractionEventData.from(e, viewport::screenToWorld);
    currentState.getInteractionMap().handleRelease(data);
});
```

## Die Vorteile dieser Erweiterung

1. **State-Isolation:** Während ein Drag läuft (`activeDrag != null`), werden keine normalen Klicks versehentlich ausgelöst.
2. **Kapselung von Undo/Redo:** In `onEnd()` des `MoveNodesDragHandler`s kannst du genau **einen** Undo-Schritt aufzeichnen (statt für jedes kleine Pixel-Delta beim Draggen).
3. **Sehr hohe Wiederverwendbarkeit:** Ein `PanViewportDragHandler` (Kamera bewegen) kann problemlos in *allen* Zuständen wiederverwendet werden.

# gemini response

Die `EditorContext`-Klasse fungiert als das **Herzstück der State Machine** (Context im klassichen State Pattern) und gleichzeitig als Schnittstelle zwischen der UI (JavaFX) und deinem Anwendungsmodell (Domain Model/Graph/Canvas).

Sie erfüllt im Wesentlichen drei Aufgaben:
1. **Zustandsverwaltung:** Hält den aktuellen `EditorState` und regelt den sauberen Übergang (`switchState`).
2. **Event-Routing:** Reicht JavaFX-Events (Klicks, Drags, Tasten) an den aktiven Zustand weiter.
3. **Services/Modell bereitstellen:** Bietet den konkreten Zuständen und Drag-Handlern Zugriff auf die Kamera/Viewport, das Datenmodell und Auswahllisten (Selection).

### Die `EditorContext`-Klasse

```java
package de.fmc.editor.state;

import javafx.geometry.Point2D;
import javafx.scene.input.KeyEvent;
import javafx.scene.input.MouseEvent;
import java.util.Objects;
import java.util.function.BiFunction;

public class EditorContext {

    // Aktueller Zustand des Editors
    private EditorState currentState;

    // Transformation von Screen- zu Welt-Koordinaten (z. B. aus der Kamera/Viewport)
    private final BiFunction<Double, Double, Point2D> sceneToWorldTransformer;

    // Zugrundeliegendes Datenmodell & UI-Layer (Beispiele)
    private final DocumentModel documentModel;
    private final SelectionModel selectionModel;
    private final Viewport viewport;

    public EditorContext(
            EditorState initialState,
            Viewport viewport,
            DocumentModel documentModel,
            SelectionModel selectionModel
    ) {
        this.viewport = Objects.requireNonNull(viewport);
        this.sceneToWorldTransformer = viewport::screenToWorld;
        this.documentModel = Objects.requireNonNull(documentModel);
        this.selectionModel = Objects.requireNonNull(selectionModel);

        // Initialen Zustand setzen
        this.currentState = Objects.requireNonNull(initialState);
        this.currentState.onEnter();
    }

    // =========================================================================
    // 1. State Machine Management (Zustandswechsel)
    // =========================================================================

    /**
     * Wechselt den aktuellen Zustand des Editors.
     * Führt automatisch die Lifecycle-Methoden onExit() und onEnter() aus.
     */
    public synchronized void switchState(EditorState newState) {
        Objects.requireNonNull(newState, "New state cannot be null");

        if (this.currentState.equals(newState)) {
            return; // Kein Wechsel nötig
        }

        // Alter Zustand räumt auf (z.B. Hilfslinien oder Overlays entfernen)
        this.currentState.onExit();

        this.currentState = newState;

        // Neuer Zustand richtet sich ein
        this.currentState.onEnter();
    }

    public EditorState getCurrentState() {
        return currentState;
    }

    // =========================================================================
    // 2. Event Routing (Schnittstelle zu JavaFX)
    // =========================================================================

    /**
     * Reicht ein JavaFX Mouse-Pressed Event an den aktuellen Zustand weiter.
     */
    public boolean handleMousePressed(MouseEvent event) {
        InteractionEventData data = InteractionEventData.from(event, sceneToWorldTransformer);
        return currentState.getInteractionMap().handlePress(data);
    }

    /**
     * Reicht ein JavaFX Mouse-Dragged Event an den aktuellen Zustand weiter.
     */
    public boolean handleMouseDragged(MouseEvent event) {
        InteractionEventData data = InteractionEventData.from(event, sceneToWorldTransformer);
        return currentState.getInteractionMap().handleDrag(data);
    }

    /**
     * Reicht ein JavaFX Mouse-Released Event an den aktuellen Zustand weiter.
     */
    public boolean handleMouseReleased(MouseEvent event) {
        InteractionEventData data = InteractionEventData.from(event, sceneToWorldTransformer);
        return currentState.getInteractionMap().handleRelease(data);
    }

    /**
     * Reicht ein JavaFX Key-Pressed Event an den aktuellen Zustand weiter.
     */
    public boolean handleKeyPressed(KeyEvent event) {
        InteractionEventData data = InteractionEventData.from(event);
        return currentState.getInteractionMap().handlePress(data);
    }

    // =========================================================================
    // 3. Service-Methoden für States & DragHandler (API für Zustände)
    // =========================================================================

    public DocumentModel getDocumentModel() {
        return documentModel;
    }

    public SelectionModel getSelectionModel() {
        return selectionModel;
    }

    public Viewport getViewport() {
        return viewport;
    }

    // Nützliche Abfrage-Methoden für Matcher (z.B. Hovering-Checks)

    public boolean isHoveringEmptySpace(InteractionEventData event) {
        return documentModel.findNodeAt(event.worldX(), event.worldY()).isEmpty();
    }

    public boolean isHoveringSelectedNode(InteractionEventData event) {
        return documentModel.findNodeAt(event.worldX(), event.worldY())
                .map(selectionModel::isSelected)
                .orElse(false);
    }

    // High-Level Editor-Aktionen (Command-Aufrufe)

    public void selectAt(double worldX, double worldY) {
        documentModel.findNodeAt(worldX, worldY)
                .ifPresentOrElse(
                    selectionModel::select,
                    selectionModel::clearSelection
                );
    }

    public void spawnNodeAt(double worldX, double worldY) {
        NodeModel newNode = new NodeModel(worldX, worldY);
        documentModel.addNode(newNode);
        selectionModel.select(newNode);
    }
}
```

### Anbindung an die JavaFX View (z. B. Canvas Controller)

In deiner JavaFX-Anwendung (z. B. in einer `Controller`-Klasse oder einer benutzerdefinierten `Pane`) musst du den `EditorContext` jetzt nur noch an die Ereignisse deiner View binden:

```java
public class EditorCanvasController {

    private final Canvas canvas;
    private final EditorContext editorContext;

    public EditorCanvasController(Canvas canvas, Viewport viewport, DocumentModel model, SelectionModel selection) {
        this.canvas = canvas;

        // Initialen Zustand festlegen (z.B. SelectState)
        SelectState initialState = new SelectState(null); // Context wird nachfolgend injiziert
        this.editorContext = new EditorContext(initialState, viewport, model, selection);

        // Event Listener auf der JavaFX Pane/Canvas registrieren
        registerEventHandlers();
    }

    private void registerEventHandlers() {
        // Maus-Events
        canvas.addEventFilter(MouseEvent.MOUSE_PRESSED, editorContext::handleMousePressed);
        canvas.addEventFilter(MouseEvent.MOUSE_DRAGGED, editorContext::handleMouseDragged);
        canvas.addEventFilter(MouseEvent.MOUSE_RELEASED, editorContext::handleMouseReleased);

        // Tastatur-Events (auf der Szene oder dem fokussierten Node)
        canvas.setFocusTraversable(true);
        canvas.addEventFilter(KeyEvent.KEY_PRESSED, editorContext::handleKeyPressed);
    }
}
```

### Die Vorteile dieser Architektur auf einen Blick

1. **Säuberste Trennung (Decoupling):** Die JavaFX View weiß nichts von den Zuständen (z. B. `SelectState`, `CreateNodeState`). Sie leitet nur Events an den `EditorContext` weiter.
2. **Kapselung von Lifecycle-Logik:** Durch `onEnter()` und `onExit()` beim `switchState` kannst du Overlays (wie z. B. temporäre Platzierungs-Vorschauen) beim Verlassen eines Zustands automatisch aufräumen, ohne dass die View sich darum kümmern muss.
3. **Kein globales Singleton:** Der `EditorContext` wird injiziert. Dadurch sind deine Zustände und Interaktionen hervorragend mit Unit Tests testbar (du kannst z. B. Mock-Objects für den `Viewport` oder das `DocumentModel` übergeben).

Hier gibt es zunächst ein kleines, aber sehr wichtiges Detail zur Klarstellung: Die Methoden **`ifPresentOrElse`** und **`map`** gehören *nicht* zur `DocumentModel`-Klasse selbst. Sie sind Methoden der Klasse **`java.util.Optional`**, die fest in Java eingebaut ist.

Da `findNodeAt` möglicherweise kein Element findet (weil der Benutzer auf eine leere Fläche geklickt hat), geben wir nicht `null` zurück, sondern ein `Optional<NodeModel>`. Und genau auf diesem `Optional` rufen wir dann `map` oder `ifPresentOrElse` auf. Das ist modernes und null-sicheres Java-Design!

Hier siehst du, wie das **`DocumentModel`** (und als Hilfsklasse das `NodeModel`) aufgebaut sein könnte, damit genau diese elegante Aufrufkette funktioniert.

### 1. Das `NodeModel` (Repräsentiert ein Element im Editor)

Damit wir herausfinden können, ob ein Punkt getroffen wurde, muss das Element wissen, wo es liegt und wie groß es ist.

```java
package de.fmc.editor.model;

public class NodeModel {
    private double x;
    private double y;
    private double width = 100.0;
    private double height = 50.0;

    public NodeModel(double x, double y) {
        this.x = x;
        this.y = y;
    }

    // Prüft, ob eine Weltkoordinate innerhalb dieses Elements liegt (Hitbox-Test)
    public boolean contains(double worldX, double worldY) {
        return worldX >= x && worldX <= x + width &&
               worldY >= y && worldY <= y + height;
    }

    // Getter und Setter (fürs Verschieben)
    public double getX() { return x; }
    public double getY() { return y; }
    public void setPosition(double x, double y) {
        this.x = x;
        this.y = y;
    }
}
```

### 2. Das `DocumentModel` (Verwaltet alle Elemente)

In einer JavaFX-Architektur nutzt man für Listen am besten eine `ObservableList`. Das hat den riesigen Vorteil, dass deine View (der Canvas oder der Scenegraph) automatisch benachrichtigt wird, wenn Elemente hinzugefügt oder entfernt werden.

```java
package de.fmc.editor.model;

import javafx.collections.FXCollections;
import javafx.collections.ObservableList;
import java.util.Optional;

public class DocumentModel {

    // Die Liste aller Elemente im Dokument
    private final ObservableList<NodeModel> nodes = FXCollections.observableArrayList();

    /**
     * Fügt ein neues Element zum Dokument hinzu.
     */
    public void addNode(NodeModel node) {
        nodes.add(node);
    }

    /**
     * Entfernt ein Element aus dem Dokument.
     */
    public void removeNode(NodeModel node) {
        nodes.remove(node);
    }

    /**
     * Gibt eine Read-Only-Liste der Elemente zurück (z.B. fürs Rendering in der View).
     */
    public ObservableList<NodeModel> getNodes() {
        return FXCollections.unmodifiableObservableList(nodes);
    }

    /**
     * Sucht das oberste Element an der gegebenen Welt-Koordinate.
     * Gibt ein Optional zurück, da der Klick auch ins Leere gehen kann.
     */
    public Optional<NodeModel> findNodeAt(double worldX, double worldY) {
        // Wir iterieren RÜCKWÄRTS durch die Liste.
        // Warum? Elemente, die später hinzugefügt wurden, werden "weiter oben" (Z-Index)
        // gezeichnet. Wenn sich zwei Elemente überlappen, wollen wir das oberste treffen.
        for (int i = nodes.size() - 1; i >= 0; i--) {
            NodeModel node = nodes.get(i);

            if (node.contains(worldX, worldY)) {
                return Optional.of(node); // Treffer! Zurückgeben.
            }
        }

        return Optional.empty(); // Nichts gefunden
    }
}
```

---

### Exkurs: Warum dieses Design so mächtig ist (`Optional`)

Weil `findNodeAt` ein `Optional<NodeModel>` zurückgibt, können wir in unserem `EditorContext` (oder unseren Matchern) extrem kompakten und sicheren Code schreiben.

Ohne `Optional` (früherer Java-Stil) sähe ein Klick-Handling so aus:
```java
NodeModel clickedNode = documentModel.findNodeAt(x, y);
if (clickedNode != null) {
    if (selectionModel.isSelected(clickedNode)) {
        return true;
    } else {
        return false;
    }
} else {
    return false;
}
```

Mit `Optional` und den Methoden `map` und `ifPresentOrElse` wird daraus deklarativer Code, der sich wie ein flüssiger Satz liest:

**Beispiel 1: Ist das Element unter der Maus ausgewählt? (`map`)**
```java
public boolean isHoveringSelectedNode(InteractionEventData event) {
    return documentModel.findNodeAt(event.worldX(), event.worldY())
            .map(node -> selectionModel.isSelected(node)) // Transformiere Node zu Boolean
            .orElse(false); // Falls kein Node da ist, ist das Ergebnis false
}
```

**Beispiel 2: Klick verarbeiten (`ifPresentOrElse`)**
```java
public void selectAt(double worldX, double worldY) {
    documentModel.findNodeAt(worldX, worldY)
            .ifPresentOrElse(
                node -> selectionModel.select(node), // WENN ein Element da ist
                () -> selectionModel.clearSelection() // WENN KEIN Element da ist
            );
}
```

### Das `SelectionModel` (mit JavaFX Observables)

Durch die Verwendung von JavaFX `ObservableSet` oder `ObservableList` können andere Komponenten (wie z. B. der Canvas oder ein Properties-Panel) direkt auf Änderungen der Auswahl lauschen.

```java
package de.fmc.editor.model;

import javafx.collections.FXCollections;
import javafx.collections.ObservableSet;
import javafx.collections.SetChangeListener;

import java.util.Collection;
import java.util.Collections;
import java.util.Set;

public class SelectionModel {

    // Ein Set ist perfekt: Ein Element kann nie doppelt ausgewählt sein
    private final ObservableSet<NodeModel> selectedNodes = FXCollections.observableSet();

    // =========================================================================
    // 1. Grundlegende Selektions-Aktionen
    // =========================================================================

    /**
     * Wählt ein einzelnes Element aus und hebt die bisherige Auswahl auf.
     */
    public void select(NodeModel node) {
        if (node == null) {
            clearSelection();
            return;
        }
        selectedNodes.clear();
        selectedNodes.add(node);
    }

    /**
     * Fügt ein Element zur bestehenden Auswahl hinzu (z. B. bei Shift+Klick).
     */
    public void addToSelection(NodeModel node) {
        if (node != null) {
            selectedNodes.add(node);
        }
    }

    /**
     * Fügt eine ganze Gruppe von Elementen hinzu (z. B. durch Selektionsrahmen).
     */
    public void addAllToSelection(Collection<NodeModel> nodes) {
        selectedNodes.addAll(nodes);
    }

    /**
     * Kehrt den Selektionsstatus um (Ist es gewählt -> abwählen; sonst wählen).
     * Ideal für Shift+Klick / Strg+Klick Toggle-Logik.
     */
    public void toggleSelection(NodeModel node) {
        if (node == null) return;

        if (selectedNodes.contains(node)) {
            selectedNodes.remove(node);
        } else {
            selectedNodes.add(node);
        }
    }

    /**
     * Entfernt ein Element aus der Auswahl.
     */
    public void deselect(NodeModel node) {
        selectedNodes.remove(node);
    }

    /**
     * Leert die gesamte Auswahl (Klick ins Leere).
     */
    public void clearSelection() {
        selectedNodes.clear();
    }

    // =========================================================================
    // 2. Abfragen (Query Methods)
    // =========================================================================

    public boolean isSelected(NodeModel node) {
        return selectedNodes.contains(node);
    }

    public boolean isEmpty() {
        return selectedNodes.isEmpty();
    }

    public int getSelectionCount() {
        return selectedNodes.size();
    }

    /**
     * Unveränderliche Sicht auf alle aktuell gewählten Elemente.
     */
    public Set<NodeModel> getSelectedNodes() {
        return Collections.unmodifiableSet(selectedNodes);
    }

    // =========================================================================
    // 3. Reactive Bindings (Observer Pattern)
    // =========================================================================

    /**
     * Erlaubt es dem Canvas oder Properties-Panel, sofort zu reagieren,
     * wenn Elemente ausgewählt oder abgewählt werden.
     */
    public void addListener(SetChangeListener<NodeModel> listener) {
        selectedNodes.addListener(listener);
    }

    public void removeListener(SetChangeListener<NodeModel> listener) {
        selectedNodes.removeListener(listener);
    }
}
```

### Was diese Klasse so stark macht

#### 1. Die Power der `toggleSelection`-Methode
Beim Interagieren in Editoren hat man oft die Anforderung: *"Wenn ich `Shift` drücke und auf ein Element klicke, soll es ausgewählt werden – war es aber schon ausgewählt, soll es wieder abgewählt werden."*

Dank `toggleSelection` schrumpft diese Logik im `EditorContext` auf eine einzige Zeile zusammen:

```java
public void toggleSelectionAt(double worldX, double worldY) {

            .ifPresent(selectionModel::toggleSelection);
}
```

#### 2. Entkoppelte UI durch `SetChangeListener`
Der Rendering-Code deines Canvas muss das `SelectionModel` nicht ständig manuell abfragen. Er kann sich einfach als Listener anhängen und automatisch neu zeichnen, wenn sich etwas ändert:

```java

selectionModel.addListener(change -> {
    if (change.wasAdded()) {
        System.out.println("Node ausgewählt: " + change.getElementAdded());
    } else if (change.wasRemoved()) {
        System.out.println("Node abgewählt: " + change.getElementRemoved());
    }

    // Canvas veranlassen, die Auswahlrahmen (Bounding Boxes) neu zu zeichnen
    canvas.redraw();

```

#### 3. Perfektes Zusammenspiel mit dem DragHandler
Wenn du aus der vorherigen Antwort den `SelectionBoxDragHandler` (Rubberband-Selektion) nimmst, kannst du am Ende des Drags direkt alle getroffenen Elemente dem `SelectionModel` übergeben:

```java
@Override

    List<NodeModel> nodesInBox = documentModel.findElementsIn(selectionBox.getBounds());

    // 2. Füge sie gesammelt zum SelectionModel hinzu
    if (endEvent.isShiftDown()) {
        selectionModel.addAllToSelection(nodesInBox);
    } else {
        selectionModel.clearSelection();
```

### Das Gesamtbild deiner Architektur

Damit schließt sich der Kreis zu deiner ursprünglichen Frage:

1. **`InteractionEventData`** $\rightarrow$ Macht Event-Daten sauber konsumierbar.
2. **`InteractionMap` / `EventMatcher`** $\rightarrow$ Ordnet Tasten/Maus-Kombinationen Aktionen zu.

5. **`DocumentModel` & `SelectionModel`** $\rightarrow$ Verwalten die eigentlichen Anwendungsdaten entkoppelt von der JavaFX-UI.
